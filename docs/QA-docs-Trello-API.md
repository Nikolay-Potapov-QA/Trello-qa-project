QA-документация: Trello API Test Framework
Этот файл объединяет три артефакта. При желании разнесите их в docs/test-plan.md, docs/test-cases.md и docs/bug-report-examples.md по заголовкам ниже.
1. Тест-план
Объект тестирования: REST API Trello (боевой сервис api.trello.com, тестовый workspace/аккаунт).
Цели тестирования: проверить, что операции создания, чтения, изменения и удаления досок, списков, карточек и чек-листов возвращают ожидаемые статусы и корректно отражают переданные данные.
Виды тестирования: функциональное тестирование API (позитивные и негативные сценарии), smoke — на каждый пуш.
Тестовое окружение: реальный Trello API с тестовым аккаунтом/workspace, каждый тест создаёт и удаляет собственные данные.
Из области тестирования исключено: UI Trello, тестирование прав доступа между разными пользователями/командами, вебхуки, ограничения rate limit API.
Критерии входа: валидные TRELLO_API_KEY и TRELLO_TOKEN в .env, доступен api.trello.com.
Критерии выхода: все тест-кейсы по CRUD-операциям над доской/списком/карточкой зелёные, отчёт Allure сформирован без ошибок инфраструктуры.
Риски:
Тесты зависят от доступности внешнего сервиса (api.trello.com) — не изолированы моком, при сбое сервиса тесты падают независимо от качества кода.
Возможные ограничения по частоте запросов (rate limits) при частых прогонах в CI.
2. Тест-кейсы
TC-01 — Создание доски с валидным именем
Шаги:
Отправить POST /boards с параметром name.
Ожидаемый результат: статус 200, в ответе присутствует id доски, name совпадает с переданным.
TC-02 — Получение доски по id
Предусловие: доска создана (TC-01).
Шаги:
Отправить GET /boards/{id}.
Ожидаемый результат: статус 200, данные доски соответствуют созданным при TC-01.
TC-03 — Удаление доски
Предусловие: доска существует.
Шаги:
Отправить DELETE /boards/{id}.
Повторно запросить GET /boards/{id}.
Ожидаемый результат: удаление возвращает статус успеха; повторный запрос доски возвращает 404 или ошибку «не найдено».
TC-04 — Создание списка внутри доски
Предусловие: доска существует.
Шаги:
Отправить POST /lists с name и idBoard.
Ожидаемый результат: статус 200, список привязан к переданной доске (idBoard в ответе совпадает).
TC-05 — Создание карточки в списке
Предусловие: список существует.
Шаги:
Отправить POST /cards с name и idList.
Ожидаемый результат: статус 200, карточка появляется в указанном списке.
TC-06 — Обновление карточки
Предусловие: карточка существует.
Шаги:
Отправить PUT /cards/{id} с изменённым названием.
Получить карточку заново.
Ожидаемый результат: новое название сохранено и возвращается при повторном запросе.
TC-07 — Архивирование карточки
Предусловие: карточка существует и не архивирована.
Шаги:
Отправить PUT /cards/{id} с closed=true.
Получить карточку.
Ожидаемый результат: поле closed = true, карточка не отображается в активном списке (в UI Trello — в разделе архива).
TC-08 — Создание чек-листа и пункта в нём
Предусловие: карточка существует.
Шаги:
Отправить POST /cards/{id}/checklists с name.
Отправить POST /checklists/{id}/checkItems с name.
Ожидаемый результат: чек-лист создан на карточке, пункт создан внутри чек-листа и виден при запросе карточки.
TC-09 — Создание доски без имени (негативный)
Шаги:
Отправить POST /boards без параметра name или с пустой строкой.
Ожидаемый результат: запрос отклоняется с ошибкой валидации (4xx), доска не создаётся.
TC-10 — Создание карточки в несуществующем списке (негативный)
Шаги:
Отправить POST /cards с idList, которого не существует.
Ожидаемый результат: запрос отклоняется с ошибкой (4xx), карточка не создаётся.
3. Чек-лист регрессии (модуль «Карточки»)

Создание карточки с обязательными полями проходит успешно

Создание карточки в несуществующем списке отклоняется

Обновление названия карточки сохраняется корректно

Архивирование карточки скрывает её из активного списка

Разархивирование возвращает карточку в список

Чек-лист корректно создаётся на карточке

Пункт чек-листа корректно создаётся и отображается

Удаление доски удаляет все вложенные списки и карточки

Повторный запрос удалённой сущности возвращает ошибку, а не пустой успешный ответ

API-ключ и токен не попадают в открытом виде ни в один лог/отчёт
4. Примеры баг-репортов
BUG-001: Архивированная карточка остаётся видимой через прямой GET-запрос без явного признака архивации
Приоритет: Low
Шаги воспроизведения:
Создать карточку.
Архивировать (closed=true).
Получить карточку через GET /cards/{id} без дополнительных query-параметров.
Фактический результат: карточка возвращается полностью, разработчику легко упустить проверку поля closed при работе с ответом.
Ожидаемый результат: (зафиксировать ожидание из документации API) — обсудить с командой, нужно ли явно отмечать в ответе, что карточка в архиве, помимо поля closed.
Примечание: не блокирующий баг, скорее заметка по эргономике API-ответа.
BUG-002: Создание чек-листа с пустым именем не отклоняется
Приоритет: Medium
Шаги воспроизведения:
Создать карточку.
Отправить POST /cards/{id}/checklists с name="".
Фактический результат: чек-лист создаётся с пустым названием, статус 200.
Ожидаемый результат: запрос с пустым обязательным полем должен отклоняться с ошибкой валидации.
BUG-003: Удаление доски не возвращает подтверждение количества удалённых вложенных сущностей
Приоритет: Low
Шаги воспроизведения:
Создать доску с 2 списками и 3 карточками.
Удалить доску.
Фактический результат: ответ на DELETE /boards/{id} не содержит информации о том, сколько вложенных сущностей было удалено.
Ожидаемый результат: (на усмотрение команды) — зафиксировать, достаточно ли текущего поведения для сценариев очистки данных в тестах, или нужен отдельный метод верификации.
